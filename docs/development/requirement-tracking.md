## Key cross-cutting findings (stabilization-critical)
- **Tenant isolation / authorization (highest priority):** Mixed access patterns. `apps/api/src/app.ts` mounts feature routes behind `authenticate` + `requireCsrf` + `resolveTenant`, and employees router uses `tenantRunner`-scoped repository/service. However `settings`, `dashboard`, `notifications`, `auth` routes and parts of `leave`/`documents`/`organization`/`onboarding`/`attendance` perform direct `prisma` reads/writes or raw tx usage with manual `companyId`/`userId` filters; this bypasses centralized tenant scoping guarantees and increases regression/cross-tenant risk. `employees.repository.sendInvitation` accesses `db.user`/`db.invitationToken`/`db.companyMembership` via tenant-scoped delegate, but `User` is intentionally global/blocked in tenant scope (`database/tenant/scope.ts`) and not exposed as a user delegate in `database/tenant/tenant-db.ts` — **likely runtime `TenantViolationError` defect**.
- **Authorization model:** `middleware/authorization/authorize.ts` and `@gsc/contracts` `can()` provide action/role checks but `can()` is not resource-aware; route-level enforcement is inconsistent across new modules. Manager/self/cross-company "not found" behavior and anti-self-approval/immutability rules are **not fully verified**.
- **Data integrity / migration:** P0 migration is additive in inspected sections (enums/tables/indexes/FKs/checks) but shows **no DB-level leave-overlap exclusion constraint/trigger**, **no append-only/immutability protection for audit logs added in P0 migration**, and limited enforcement for pending-correction uniqueness/concurrency beyond app checks. `employee_audit_logs` candidate migration includes REVOKE UPDATE/DELETE/TRUNCATE guard; applied/common audit-log immutability posture requires DB validation. Employee number generation uses app/tx raw sequence logic — concurrency/immutability safety **unverified**.
- **Compatibility regression:** `packages/contracts/src/employees.ts` and employees implementation changed request/response shapes and validation (e.g. create requires `workEmail`, `departmentId`, `joiningDate`; expanded fields/status/audit behavior). Existing `employees.api.test.ts` now has **10 failures** (400 vs expected 201/404/409, 500 on status flows, audit/no-op semantics differ), indicating **breaking changes and/or defects** in employees module or outdated tests/fixtures (`modules/employees/testing/fake-prisma.ts` does not model new schema/contracts). Existing web consumers/tests not revalidated.
- **Auth/session/CSRF:** Bearer and `gsc_session` cookie auth, session hash/expiry/idle checks, CSRF enforcement for unsafe cookie-auth, and ACTIVE membership resolution exist; end-to-end PRD acceptance (exact expiry/idle behavior, multi-company selection contract, token delivery/redaction, lockout semantics, cookie/security behavior across environments) remains **unverified**. Login failure tracking is in-memory/process-local.
